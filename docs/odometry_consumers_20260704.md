# 里程计（Dead-Reckoning）消费者梳理

日期：2026-07-04

范围：梳理 route memory 非 oracle 定位链路里，里程计（每一步的机身增量 dx/dy/dtheta，来源可以是 `--measured_odometry` 或 `--leg_odometry`）实际被用在哪些地方、各自的作用机制是什么。2026-07-03 的"里程计消费者审计"（README 记录）从代码里数出一共 6 个真实消费者，本文对这 6 个消费者逐一展开写清楚，并补充了本次（2026-07-04）`--leg_odometry` 单集验证失败排查过程中确认的一个结论：**这 6 个消费者构成的整条链路，在 `--route_hint_source=oracle` 模式下全程仍然运行，但只作为"影子"记录，不会真正影响机器人的动作**——只有非 oracle 模式下，它们的输出才会真正驱动导航。

主要代码位置：

- 里程计每一步增量的产生：`code/round_trip_eval.py`（`get_measured_action_delta` / `get_leg_odometry_action_delta`）
- 六个消费者全部实现在：`code/route_memory_agent.py`
- 朝向一致性门控的调用点：`code/round_trip_eval.py` 里传给 `code/relocalization.py` 各后端的 `dead_reckoning_yaw_rad` 参数

## 大前提

每一步，里程计给出的只是一个很朴素的量：**这一小步机身往前走了多少、往侧边挪了多少、转了多少角度**（一个 `[dx, dy, dtheta]` 三元组）。这个小碎片本身不是任何决策，它的价值全在于被下面六个地方分别拿去使用。

且六个消费者是 route memory "影子"链路的一部分：只要开了 `--route_memory`，不管 `--route_hint_source` 选的是不是 oracle，它们全程都在跑。区别只在于：

- `--route_hint_source=oracle` 时，它们算出来的东西只被写进 `route_memory_shadow` 之类的诊断字段做事后分析，不影响机器人实际怎么走（VLM 看到的提示和 stop-gate 用的距离都直接读仿真器真值）。
- 非 oracle 模式（`integrated` / `isaac`）下，它们算出来的东西就是机器人实际收到的导航依据。

## 六个消费者

### 1. 持续位姿累加（基础设施，不单独算门控或产出）

每一步都把 `[dx, dy, dtheta]` 叠加到"从出发点走到现在"和"从掉头返程那一刻走到现在"这两条持续更新的轨迹上（`update_outbound_motion` / `update_return_motion` 里的 `compose_pose`）。后面所有消费者的计算都建立在这条不断累加的轨迹之上——这也是里程计误差会像滚雪球一样越滚越大的根本原因：每一步的小误差都被永久叠加进这条轨迹里，不会自己消失，只能等第 4 项的锚点匹配把它拉回正轨。

### 2. "还剩多远回到起点"的置信度预测（`ArcLengthParticleFilter.predict`）

系统专门维护一个一维粒子滤波器，估计"沿路线还剩多少距离才能走回起点"（一堆候选距离值，每个值带一个可信度权重）。每一步，里程计告诉它这一步"往前挪了多少"（只取前向分量，侧向分量不算前进），这堆候选点就整体往前移动相应的距离，同时因为运动带来的不确定性，权重分布会变得更分散。如果距离上次被采信的匹配已经过去很久（超过 3 米没有新观测），额外的不确定性还会加速注入，让滤波器更快意识到自己"可能已经不准了"。这个分布只有在新的锚点匹配被采信时才会被拉回集中。

### 3. 生成提示文字里的距离/方位数字（`_arc_length_progress`，仅非 oracle 模式下真正驱动导航）

如果没开 oracle 真值，每次要生成"你离目标还有多远、该往哪转"这句话喂给 VLM 时，这个数字的来源是：**"上一次被采信的锚点匹配结果所在的位置" + "从那次匹配到现在，里程计说自己又往前挪了多少"**。也就是说，只要没有新的匹配被采信，这句提示完全靠里程计一步步垫出来——这正是"漂移"真正累积、并且直接体现在 VLM 输入里的地方，时间拖得越久这个数字偏离真实情况就越远。

### 4. 判断新锚点匹配"合不合理"的门控之一（`_sequence_match_observation` 的运动误差门控）

每当有一个新的候选匹配结果出现（比如"现在最像是站在第 5 个锚点旁边"），系统会先用里程计算一个"按道理现在应该在路线上的什么位置"（= 上一次被采信的位置 + 里程计说的累积前进距离，即"expected_s"），再拿候选结果自己声称的位置去对比：

- 如果候选结果说"其实是倒退了一大截"，超过一个很小的容忍范围（默认 0.4 米）就直接拒绝，不给第二次机会；
- 如果候选结果说"突然一下子前进了一大截"（超过默认 2 倍锚点间距，比如直接宣称已经到终点），则要求连续两次独立的匹配都指向差不多的位置，才肯采信（这条是 2026-07-02 ep680 永久锁死事故之后加的第二道保险）。

这两条判断标准，都是拿里程计给出的"预期位置"当参照物，所以里程计本身的误差大小会直接决定这道门控是"太严格拒掉了正确匹配"还是"太宽松放过了错误匹配"。

### 5. 判断候选匹配"朝向合不合理"的门控之二（`dead_reckoning_yaw_rad` 朝向一致性门控）

基于点云匹配（ICP / Scan Context）的定位方式有个通病：同一条走廊两头长得几乎一样，容易把"朝这边"误判成"其实朝反方向"（180° 镜像）。这里的做法是：把里程计从出发那一刻起累积到现在的朝向角度（`route_agent.current_absolute_pose_from_start()` 的第三个分量）当作参照基准，传给 `local_map_anchor_relocalization` / `scan_context_anchor_relocalization` / `fused_anchor_relocalization` 等后端；任何候选匹配算出来的朝向如果跟这个基准差得太多（超过 90°）就直接判定是镜像误判，否决掉。

需要注意：这是一个**长期、从出发时刻起累积**的朝向参考，本身也会随时间漂移（2026-07-02 曾实测单集漂移到 160°），所以这道门控目前是"用一个本身也不准的基准去判断别人准不准"，效果上限受里程计朝向精度的直接制约——README 里记录的"orientation-drift 参考修复"待办（改用局部相对窗口而非全局累积参考）就是针对这个问题，目前仍未实现。

### 6. 锚点与锚点之间的相对边（`edge_from_previous` / `_compose_edges_between`，2026-07-02 加入）

出发过程中每记一个新锚点，都会顺带用当时的里程计累积量算出"这个锚点相对上一个锚点走了多少"，存成一条"边"（`edge_from_previous`）。之后如果系统想知道"现在相对锚点 A 的位置，换算成相对锚点 B 是多少"（`_reproject_delta_to_anchor`，被第 3、4 项的候选融合逻辑调用），不会直接拿 A、B 各自从出发点算起的位置相减——那样会把两条独立路径各自累积的全部误差都叠加进来，两个越远的锚点误差越大；而是沿着 A 到 B 中间这几条"边"一站一站串起来算（`_compose_edges_between`），只累积中间这几跳的误差，通常只有 1-2 跳，精度比直接相减好得多。

## 小结归类

- **基础设施**：第 1 项（持续累加）、第 6 项（锚点间相对边）——为其余四项提供输入。
- **直接产出数字**：第 2 项（剩余距离置信度）、第 3 项（提示文字距离/方位）。
- **接受/拒绝门控**：第 4 项（运动误差）、第 5 项（朝向一致性）。

## 与 2026-07-04 leg_odometry 单集验证的关系

`--leg_odometry` 单集验证（ep187，oracle + fused + stop_gate + hint_arbiter 配置）return 失败、`distance_to_start=3.055m` 卡在 `stop_gate` 的 `r_in=3.0m` 门槛外沿原地打转，最终超时判定失败。经代码追踪确认：该配置下 `--route_hint_source=oracle`，VLM 实际看到的提示和 `stop_gate` 用来判断的距离，都来自 `direct_oracle_route_anchor_progress`（直接读取仿真器真值位姿），**完全不经过本文列出的六个消费者**。因此这次 return 失败可以排除是 `--leg_odometry` 里发现的 `ground_clearance` 支撑相判定 bug（见 batch_logs/leg_odometry_smoke_ep187_20260704）造成的连锁影响，更像是 VLM 自身的采样随机性——但这一点仍待用一次不带 `--leg_odometry` 的同配置对照跑来实锤。
