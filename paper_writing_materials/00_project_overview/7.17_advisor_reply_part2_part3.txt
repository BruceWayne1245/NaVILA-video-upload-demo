Part Two：当前方案主要修复的是哪一层原因（回复 Chengxu 的第二个问题）

结论先行

在 Part One 已确认 Layer 1（NaVILA 自身闭环稳定性缺陷）与 Layer 2（round-trip 语境本身的结构性干扰）相互独立、但会彼此叠加的基础上，我们认为：路线记忆-提示机制能将 Return 成功率从约 35% 提升到 94.4%，其作用机制并不是消除了 Layer 2 的根本诱因（视觉历史残留、反向视角识别混淆等），而是在 Return 全程持续为 VLM 提供一个可靠的当前位置锚点——这正是 Layer 1 的失败模式所指认的缺失环节。也就是说，Layer 2 造成失败的具体行为通道与 Layer 1 是同一个通道；当前方案修复的是这个共享通道，而不是 Layer 2 本身。

1. 证据：提示机制的作用路径指向 Layer 1 的行为通道

证据 A（干预方式）：报告第 2 节已给出的 348 次 Return 决策统计中，真正发生纠正性干预的仅占 4.3%，另有 51.7% 是 VLM 自身动作本就与提示一致。这说明提示信息的主要作用路径是通过注入 VLM 决策上下文的文本内容持续补上位置锚点，而不是靠仲裁器接管动作序列——与 Layer 1 结论中"VLM 的到达判断和动作选择缺少可靠的真实位置锚点"这一表述在机制上直接对应。

证据 B（剂量-反应关系，investigations/2026-07-15-50ep-batch-current-next-simultaneous-failure/FINDINGS.md）：50 集非 Oracle（shadow）验证中，Return 成功的 14 集平均逐集中位方位误差为 4.84°，失败的 8 集为 55.18°。失败集内部的具体行为进一步印证了这一点：8 例中 5 例是长时间原地振荡、无有效前进，3 例是 VLM 在远离终点处自主判定到达并 stop——分别与 Layer 1 记录的振荡与提前误判到达完全对应，只是触发条件从"完全没有提示"变成了"提示不准确"。

证据 C（排除语境混淆重新发作）：同一份分析（Part 4）核查了失败集的真实轨迹，nearest_reference_path.distance_m 全程保持在约 1–2 m 以内，即机器人始终未偏离已记录路线。这排除了"提示不准 → 机器人被带入未知区域 → 重新触发 Layer 2 式语境混淆"这一替代解释：提示不准时复发的是 Layer 1 式的行为不稳定，而非 Layer 2 的独立触发。

三点合在一起给出一个可验证的对应关系：提示信号的位置锚定能力越强，Layer 1 式的行为症状出现得越少；这一关系在 Oracle（提示完全准确）和 shadow（提示存在噪声）两种条件下一致成立。

2. 结论表述

Round-trip 场景下的 Return 失败由两个独立但通过同一行为通道叠加的原因构成（详见 Part One）。我们提出的路线记忆-提示机制并不需要、也没有尝试解决 Layer 2 的根本诱因；它通过持续提供可靠的位置/方位锚点，直接压制两层原因共同作用于同一行为通道（振荡决策、误判到达）所产生的下游症状。50 集非 Oracle 验证中提示准确度与失败行为类型之间的剂量-反应关系，以及失败发生时机器人始终未偏离已知路线这一事实，共同支持这一机制解释：Oracle 条件下 94.4% 的 Return 成功率并不代表 round-trip 语境的固有混淆被消除，而代表其下游行为后果被持续的位置 grounding 有效抑制。

3. 局限

目前的证据是相关性/剂量-反应式的，尚未有一次严格控制"仅改变是否提供连续提示、round-trip 语境本身保持不变"的对照实验。2026-06-16 那批用于 H1/H2 分析的原始轨迹数据目前已不在仓库中（GitHub 和本地 eval_results/ 均已被后续实验覆盖），若需要更严格的因果证据，需要重新设计并运行这样一组对照，可作为 dissertation 的 future work 单独列出。

Part Three：65% Anchor 准确率与"先测量"的问题（回复 Chengxu 的第三个问题）

1. 已有的真实闭环数字

Chengxu 的要求是"停止打磨 ICP，先把它接入闭环 Return 跑一次，拿到真实数字再决定"。这个测量在报告提交前后实际上已经独立做过了：investigations/2026-07-15-50ep-batch-current-next-simultaneous-failure/FINDINGS.md 记录的 50 集 shadow-vs-no-hint 同日同集合对照，在 outbound 成功的前提下：

- Shadow（非 Oracle，65% 左右 anchor 精确匹配率、约 65.5%/65.3% current/next 精确率的相同一套 relocalizer）：Return 成功率 66.7%（14/21）
- 无提示 baseline：41.2%（7/17）
- Oracle（上限对照）：约 87.5–94.4%（不同批次口径略有差异，见报告第 2 节）

这就是"接入闭环、拿到的真实数字"：65% 左右的 exact anchor 匹配率，在真正驱动导航时，把 Return 成功率从 41.2% 抬到 66.7%，但仍与 Oracle 上限有明显差距。

2. 65% 这个数字为什么不能直接当作"风险程度"读

进一步拆解发现，35% 的"anchor 未精确匹配"里，绝大部分是无害的。investigations/2026-07-12-promotion-fix-live-ab-and-next-behind-decomposition/FINDINGS.md 用严格标准（机器人真实位置是否已经越过尚未晋升的 anchor）重新核查后，真正意义上的"next anchor 被机器人物理超越"仅占全部尝试的 0.05%——绝大多数不精确匹配只是晋升投票机制设计内的确认延迟，本身不构成风险。

真正的风险集中在一个结构性更窄、也更可定位的失败类别：investigations/2026-07-15-.../FINDINGS.md Part 5-6 发现，Return 失败的 8 集里，误差并非均匀分布在所有 anchor 上，而是集中在每集 1–3 个 anchor 上（占该集全部读数的 30–73%），且这些位置往往是 current 和相邻的 next 候选同时读数不准——而现有的 quarantine 机制按设计从不监控 current 角色，promotion 机制唯一的超时处理是放宽晋升门槛而非跳过候选，因此这种"两边同时失准"的场景是现有机制结构性无法绕开的。这个划分（多数误差无害的时序滞后 vs. 少数集中的双边同时失准）才是"65% 准确率具体意味着什么"的真实答案，比单看一个汇总百分比更能说明该往哪投入下一步工作。

关于"07/13-07/15 期间已经把角度误差 >10° 的比例降到约 10%"：核实到的具体数字序列是——07-13 跨批次汇总（修复前，原始 ICP）稳定在约 32.6–32.7%；07-14（shadow_hint_swap_hard11_20260713，dtheta 修复后）整体 34.8%，排除已知的单个退化严重的 episode（ep367）后为 17.8%；07-15（50 集验证）中，成功集的平均值是 28.2%，失败集是 71.7%。没有找到精确对应"10%"的数据点，比较接近的是 07-14 排除单一坏 episode 后的 17.8%。引用前建议核对具体是哪个批次/口径，避免数字口径不一致。

3. Fallback：系统不确定时怎么办

investigations/2026-07-16-current-role-confidence-ambiguity-gate/ 是对这个问题的直接回应。设计原则是"弃权而非禁用"（abstain, not ban）：当 yaw 多假设竞争信号（icp_best_to_second_score_ratio）显示当前读数存在歧义时，只对这一次读数下调其上报置信度，转交给已有的 hint_action_arbiter/stop_gate 置信度门控去决定是否采信，而不永久拉黑候选、也不强行做决策。这个设计明确是吸取了 07-15 当天另一个方案（quarantine_next_quality_enabled，永久拉黑候选）的教训——后者被发现会在自相似路线上连环拉黑，最终耗尽整条路线的候选。

离线仿真评估（同一文档 Part 3）给出的是一个诚实、分场景的结果：对 3 个误差集中在单一 anchor 上的失败集（134/367/498）能给出干净、近乎即时的保护；对 1 个（708）是延迟保护；对 3 个误差弥散在整条路线上的自相似路线（319/354/214）效果退化为"接近整段都不信任提示"（不算错但不精确）；对 1 个不属于定位误差问题的失败（994，VLM 自身无视了正确的"继续走"提示）完全无效。22 集实盘验证已于 07-16 启动，但截至最后一次查看 investigations（07-17），结果尚未整理成文档。

4. 综合表述

我们已将 non-Oracle relocalization 模块接入闭环 Return 实测：在约 65% 的 anchor 精确匹配率、约 65.5%/65.3% 的 current/next 精确率条件下，Return 成功率为 66.7%，优于无提示 baseline 的 41.2%，但仍低于 Oracle 上限。进一步分析表明，35% 的"不精确匹配"中，绝大多数（严格核查下 99.95%）只是晋升机制设计内的确认延迟，不构成真实风险；真实风险集中在少数（每集 1–3 个）current/next 同时失准的 anchor 上，这是现有晋升/隔离机制结构性无法覆盖的场景，也是后续 ICP/多帧融合工作的主要目标，而非笼统地"继续打磨 ICP 整体精度"。针对系统自身无法判断可信度的情形，我们已实现并单元测试了一个"弃权而非禁用"的置信度门控机制，将不确定读数交还给已有的仲裁/停止逻辑处理而非强行决策或永久拉黑，其闭环实盘验证正在进行中。
