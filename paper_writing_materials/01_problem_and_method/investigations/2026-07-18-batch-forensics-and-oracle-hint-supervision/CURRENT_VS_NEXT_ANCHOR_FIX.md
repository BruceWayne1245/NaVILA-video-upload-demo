# 2026-07-18 (continued): the injected hint has ALWAYS reported "current," never "next" — a pervasive architectural mismatch, not an ICP-accuracy problem. Fixed behind a new opt-in flag; three live batches queued to test it.

## 0. How this was found

While reviewing a detailed 22-episode statistical breakdown (see §2 below) of `shadow_hint_swap_50ep_20260714_accumulated` (the reference batch behind this project's "14/22=63.6%" baseline number), the user asked what `progress.target_anchor_index` actually refers to — specifically, whether the hint's reported distance/bearing describe the vector to the "next" anchor (the upcoming, forward target a navigating robot needs) or something else. This was verified directly against live code, not assumed, and the answer is: it has always been "current" — the anchor most recently confirmed/promoted to, never "next."

## 1. The bug, verified from code and real data

**Code** (`route_memory_agent.py`, `_select_sequential_pair_relocalization`): `self._target_anchor_index` starts at `anchors[-1].index` (the return-start anchor) and only ever advances via `self._target_anchor_index = int(next_idx)` at the exact moment `next_est` is promoted. On every other attempt, `selected = current_est` — the anchor most recently promoted TO, re-estimated fresh each attempt via ICP against the robot's current position. `_anchor_progress_from_estimate` sets `target_anchor_index=int(anchor.index)` straight from whichever estimate was `selected` (almost always `current_est`). **`next_est`'s own position estimate — before it clears promotion — has never been exposed in the injected hint text at any point in this project's history**, despite the hint text's own hardcoded label calling it a "next-anchor vector" (a second, independent labeling bug reinforcing the wrong mental model for anyone reading raw hint text).

**Real hint text, pulled directly from `ep367`'s measurement JSON** (`round_trip.phase_events`, `event=="route_memory_hint"`), grouped into within-dwell runs (same `target_anchor_index` across consecutive attempts, no promotion in between):

```
anchor A11, n=15 attempts, bearing sequence: [-43, -76, -88, -137, -172, -173, -173, -155, -135, -135, -135, -135, -166, 12, 164]
anchor A8,  n=13 attempts, bearing sequence: [172, -123, -148, -152, -132, -124, -113, 78, -169, -141, -130, -121, -148]
anchor A7,  n=21 attempts, bearing sequence: [90, 71, 70, 66, 66, -150, 68, -153, -147, -135, -103, -151, 156, 157, -175, -167, -179, -165, -155, -126, -98]
```

Real injected text: `"[System Hint: route anchor A7 is 1.88 m away, 156 deg to your left; estimated remaining route via anchor is 8.93 m; next-anchor vector dx=-1.72 m, dy=0.77 m.]"`. Bearing frequently sits in the ±150-179° range — i.e. the named anchor is close to **directly behind the robot** — while the label still calls it a "next-anchor vector." Distance/bearing do **not** follow a clean deterministic sawtooth within a dwell (noisy, genuine ICP variance), but the "often near-antipodal" pattern is real and repeats across every dwell checked.

**Root architectural mismatch, confirmed by reading `--route_hint_source=oracle`'s own generator** (`round_trip_eval.py::direct_oracle_route_anchor_progress`): computes `current_s` = the robot's TRUE (privileged) arc-length route position every single attempt, then targets the anchor nearest `current_s - lookahead_m` (default ≈1 anchor spacing) — i.e. continuously, predictively looks ~1 spacing **ahead** of true position, refreshed from ground truth every attempt. The shadow path's "current" is the opposite in spirit: a discrete, reactive, held-static-between-promotions pointer to where the robot **was** last confirmed — and since promotion only fires once the robot is already very close to the candidate, it falls further **behind** the robot's true position for the entire remainder of each dwell. Oracle and shadow hints were never reporting analogous things despite an apparently shared "route anchor A{idx} is X m away" text format.

**Meta-finding on why this went unnoticed through the entire 2026-07-07-through-07-16 bearing-error investigation line** (including this session's own Metric 3, before this correction — see §2): every prior accuracy metric computed `|reported bearing to the SAME reported anchor − ground-truth bearing to that SAME anchor|`. By construction this only ever measures ICP noise around whichever target got selected, and is structurally blind to whether the selected target itself was the right thing to report. A perfectly-converged ICP fit on a target 170° behind the robot scores as "zero error, high confidence" on every metric used throughout this project's history while being operationally close to useless. The variable name `target_anchor_index` and the "next-anchor vector" text label both actively primed the wrong mental model.

**Why no new "next reliability" logic is needed**: `quarantine`, `quarantine_next_quality`, and `short_baseline_disambiguation`'s `anchor_heading_reliable` downgrade were all already built specifically to judge the "next" role's trustworthiness — that is the entire reason "current is never monitored" was flagged as the 2026-07-15 structural gap in the first place (`investigations/2026-07-15-50ep-batch-current-next-simultaneous-failure/`). Reporting next just needed to consume machinery that already existed.

## 2. The 22-episode statistical breakdown that led here (all outbound-success episodes of `shadow_hint_swap_50ep_20260714_accumulated`: `4,5,89,134,187,214,268,295,319,354,367,368,408,430,488,498,500,647,708,994,1038,1040`)

Ground truth throughout: robot's true position (trajectory JSONL) projected onto the nearest anchor-to-anchor segment via the exact same method `oracle_anchor_segment_return_yaw` already uses in production (`round_trip_eval.py`), giving `true_current_idx`/`true_next_idx` fresh per attempt — never read from any smoothed/reported field.

**Metric 1 — current-role anchor accuracy** (`reported_current_idx − true_current_idx`, n=10,251 pooled): exact=15.0%, behind‑1=35.1%, **behind‑2+=44.6%**, ahead+1=2.2%, ahead+2+=3.1%. Overshoot concentrated almost entirely in `ep5` (19.2%), `ep430` (32.5%), `ep488` (7.2%); exact-match rate ranges from 48.6% (`ep319`, a failure episode) down to 0.5% (`ep367`, the worst dwelling episode).

**Metric 2 — next-role accuracy, strict vs. loose "behind"** (n=9,811): exact=14.0%, ahead+1=1.6%, ahead+2=0.6%, ahead+3+=2.2%. **LOOSE** measure (`next_offset<0`): 81.7% — this is the trap: it conflates ordinary `bounded_evidence` confirmation lag (next hasn't accumulated enough votes yet — normal, intended behavior) with genuine failure. **STRICT** measure (robot's true position has physically overtaken the anchor still labeled "next" — `true_current_idx < reported_next_idx`): **2.75%**, a **29.7× gap** vs. the loose number. The strict 2.75% is not spread across episodes — concentrated in exactly 3: `ep430` (32.75%), `ep5` (14.36%), `ep647` (2.34%); **all other 19 episodes show exactly 0.00%**.

**Metric 3 — ICP/hint numeric accuracy against the reported (current) anchor's own ground truth** (n=10,251): distance error >0.5m = **40.9%**; bearing error >10° = **48.5%**. This metric measures whether the ICP estimate of whichever anchor got reported is accurate — it says nothing about whether that anchor should have been reported at all (see §1's meta-finding — this is exactly the blind spot).

**Metric 4 — `hint_action_arbiter` effectiveness and gate precision** (n=51,165 return-phase steps): no-conflict (`vlm_action_consistent`) = 22.0%; override executed = 16.9%; blocked despite a real conflict = 61.1% (`low_relocalization_confidence`=18,949, `target_too_close`=9,691, `occupied_in_local_map_path`=2,633). Gate precision (does the arbiter's `desired_bearing_deg` agree with the true bearing to `true_next_idx`?) @45° threshold: TP (justified block)=63.1%, **FP (missed opportunity — the blocked action was actually correct)=36.9%**; @30°: TP=74.4%, FP=25.6%. Extreme per-episode spread: `ep89` (10.0% FP) vs. `ep408` (89.8% FP).

## 3. Fix implemented

`route_memory_agent.py` + `round_trip_eval.py`, off-by-default, zero live behavior change verified via `py_compile` + full suite (266 tests, up from 261 before this fix; only the pre-existing unrelated `cv2`-missing `test_loftr_matching.py` error; zero regressions; 5 new tests in `SequentialPairReportNextAnchorTest`):

- New `RouteMemoryAgent.__init__` param/attribute `sequential_pair_report_next_anchor: bool = False`.
- New instance field `self._latest_next_candidate_relocalization`, populated in `_select_sequential_pair_relocalization` right before its return (`if next_est is not None: self._latest_next_candidate_relocalization = next_est` — captures the post-closure-precheck, post-short-baseline-downgrade version, the same object used for promotion voting; mirrors `_latest_relocalization`'s own "hold the last accepted value, don't clear on a reject" convention).
- `_anchor_progress()` now prefers `self._latest_next_candidate_relocalization` over `self._latest_relocalization` when the flag is on and a next-role estimate exists; falls back to current's estimate otherwise (e.g. at the final anchor, or next's ICP failed on the attempt that produced the latest accepted observation). **Does not touch the underlying (current, next) pair-tracking, promotion-vote, quarantine, or closure-check logic at all** — only which role's estimate feeds hint-text generation changes.
- New CLI flag `--sequential_pair_report_next_anchor` in `round_trip_eval.py`, wired through to the `RouteMemoryAgent(...)` constructor call and the measurement-JSON config-logging dict, matching every other `sequential_pair_*` flag's existing pattern.
- **Deliberately deferred, not fixed this session**: the hint text's hardcoded "next-anchor vector" label (`_make_anchor_hint`) is not yet made role-aware (would require threading a role parameter through `_anchor_progress_from_estimate`, which has a second, unrelated caller — `_relocalization_consistency_error` — that must not be affected, without changing flag-off behavior). Left as a known, minor, cosmetic residual: the label is now actually TRUE in the common case once the flag is on, only potentially inaccurate in the rare current-fallback case.

## 4. Live batches — three-stage queue, isolating one variable each

Per explicit user priority call: this fix jumped ahead of the previously-queued oracle-hint-supervision experiment (see `FINDINGS.md` in this same folder), since it's more fundamental and the oracle-supervision experiment's Category-A premise ("hint content is often wrong") needs reinterpretation now that a likely root cause has been found and fixed.

1. **`shadow_multiframe_submap_report_next_22ep_20260718`** (22-episode subset, matching the known 14/8 baseline split) — the 2026-07-16 motion-integrated multiframe-submap mechanism (expanded anchor coverage: symmetric ±1.5m outbound accumulation + 1.0m return-side live buffer) **plus** `--sequential_pair_report_next_anchor`. This is a restart: the original `shadow_multiframe_submap_22ep_20260716` batch (launched 07-16, resumed/relaunched 2026-07-18 morning after recovering from a stuck chain script — see `FINDINGS.md`) was killed mid-episode (`ep368`, ~3h in) once this bug was found, since the user judged that testing any mechanism on top of the old "reports current" hint had no analytical value.
2. **`sequential_pair_report_next_anchor_50ep_20260718_accumulated`** (full 50-episode set) — the cleanest, most direct test: byte-identical config to `shadow_hint_swap_50ep_20260714_accumulated` (the reference 14/22 baseline run) plus only this one new flag. No other 2026-07-16 mechanism stacked.
3. **`oracle_hint_supervision_report_next_50ep_20260718_accumulated`** (full 50-episode set) — the previously-designed oracle-supervision experiment (privileged-oracle interception: suppress hint text >10° bearing error, block hint_action execution >45° bearing error), now stacked on top of `--sequential_pair_report_next_anchor` rather than tested against the old current-reporting baseline in isolation, per the same user call.

**Operational incident during the restart, worth recording**: the first kill of the original batch-3 run only sent `SIGTERM` to the top-level wrapper script and force-killed the *current* episode's process group — it did not kill the *inner* `run_oracle_anchor_50ep_batch_20260714.sh` batch-loop process (a separate bash process, orphaned rather than terminated when its parent died). That orphan kept running autonomously with the **old** (pre-fix) config, advancing to `ep408` and running concurrently with the newly-launched fixed batch, causing GPU/VLM-port contention that cost the new batch's first 3 episodes (`ep4`, `ep5`, `ep134`) to timeout (`exit_code=98`). Found and fully killed (`kill -9` on both the orphaned driver PID and its child process groups) once GPU utilization/contention was investigated; the new batch recovered cleanly from `ep187` onward. **Lesson for future kills of a similarly-nested batch driver (`run_X.sh` → `run_oracle_anchor_50ep_batch_20260714.sh` → per-episode `timeout`-wrapped Isaac/VLM process groups): always verify via `ps aux | grep run_oracle_anchor_50ep_batch` that the middle-layer driver is actually gone too, not just the top wrapper and the currently-running episode.** `ep4`/`ep5`/`ep134` will need a separate rerun for complete 22-episode coverage in batch 1 above.
