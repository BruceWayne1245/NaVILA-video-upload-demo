# Canonical `sequential_pair` config (as of 2026-07-19, updated same day)

This file tracks the currently-adopted `sequential_pair` flag configuration for live batches, and is meant to be updated in place going forward rather than superseded by a new file each time. Seeded from the validated `shadow_hint_swap_50ep_20260714_accumulated` baseline (the 14/22=63.6% round-trip reference), verified directly against that batch's own measurement JSON (`round_trip.*` config fields), with four deliberate changes from that baseline: **`--sequential_pair_closure_check` is re-enabled**, **`--sequential_pair_closure_reconciliation_signal` is switched from `dtheta` to `bearing`**, and **`--sequential_pair_report_next_anchor` + `--sequential_pair_report_next_anchor_suppress_if_stale` are both now on** (see rationale below for each). Everything else is unchanged from the 14/22 baseline. Live re-validation launched 2026-07-19: `canonical_report_next_50ep_20260719_accumulated` → (chained) `oracle_hint_supervision_canonical_report_next_50ep_20260719_accumulated`. **A code fix landed the same day (see "Why `closure_reconciliation_signal` is now `bearing`, and the deferred-reject fix" below) that has not yet been live-batch-validated with this specific flag combination — the next canonical batch after this file's edit is the first real test of it.**

## Full flag table

| Flag | Value | Monitors | What it does / why it exists |
|---|---|---|---|
| `--sequential_pair_anchor_geometry_source` | `accumulated` | infra (both) | Anchor-to-anchor geometry for reprojection/cross-check uses the non-privileged edge chain, not oracle ground truth. |
| `--sequential_pair_closure_check` | **`True` (changed from 14/22's `False`)** | both | Cross-checks the simultaneously-read current-anchor and next-anchor ICP fits against each other every attempt; reconstructs the weaker side from the stronger on a one-sided mismatch, or (2026-07-19 code fix) counts as an explicit failed promotion vote — no longer silently drops the attempt — when neither side's quality dominates. | `--sequential_pair_closure_belief_trust_aware_guard` | `False` (unchanged) | both | Only relevant in `belief` mode — not in effect while `closure_mode=threshold`. |
| `--sequential_pair_quarantine` | `True`, mode=`trend` | next only | Permanently bans a next candidate from ever promoting if its disagreement vs. current doesn't shrink as the robot approaches. Explicitly never monitors current. |

| `--sequential_pair_short_baseline_disambiguation` | `True` (min_travel=0.3m, max_rotation_disagreement=20°) | next only | Cross-checks a next candidate's ICP reading against a second reading from a different vantage point; sets `anchor_heading_reliable=False` on disagreement (does not correct, only flags). |
| `--sequential_pair_disable_temporal_smoothing` | `True` (unchanged) | current only | Keeps `_temporally_smooth_relocalization` (across-time EMA blend of current's own successive readings) turned OFF — see rationale below, this is the mechanism actually proven harmful. |
| `--sequential_pair_closure_reconciliation_signal` | **`bearing` (changed from 14/22's `dtheta` default)** | both | Which quantity `closure_precheck` uses to decide current/next agree or disagree. `dtheta` (the ICP-estimated rotation) was already known unreliable (07-13: median 38° error vs. bearing's 2.2°, r≈0.40 correlation between the two on the same readings) but had never been switched here specifically — see "Why `closure_reconciliation_signal` is now `bearing`" below. |
| `--sequential_pair_loftr_rear_yaw_check` | `False` (unchanged) | diagnostic only | Off — expensive, diagnostic-only, not part of live decision-making regardless. |
| `--sequential_pair_report_next_anchor` | **`True` (changed from 14/22's `False`)** | hint source | Reports the "next" role's own estimate in the injected hint instead of "current" — the historically-correct intent (matches the hint text's own "next-anchor vector" label, which had silently described current for this project's entire history until 2026-07-18). | `--sequential_pair_report_next_anchor_suppress_if_stale` | **`True` (new, 2026-07-19)** | hint source | No-op unless `report_next_anchor` is also on. See "Why suppress_if_stale is on" below. |

| Flag | Status | Why excluded |
|---|---|---|

| `--sequential_pair_current_confidence_ambiguity_gate` | off | 2026-07-16: real, validated signal (caps reported confidence for one attempt when current's own ICP is ambiguous) but only offline/small-live-sample tested; not yet folded into a validated main config. |
| `--sequential_pair_short_baseline_require_resolution` | off | 2026-07-16: fixes short_baseline_disambiguation's 0.1%-firing under-triggering bug by withholding promotion until resolved (bounded by a stall valve). | `--route_memory_multiframe_anchor_symmetric_enabled` / `--route_memory_return_frame_buffer_enabled` | off | 2026-07-16: real, motivated mechanism (extends anchor/current capture from a single instantaneous frame to a real motion-integrated submap) but a same-episode/same-anchor `covisibility_records` comparison (2026-07-19, `ep319` anchor 3) found it makes matching measurably *harder* (overlap_ratio 0.550→0.317, confidence 0.505→0.310, match_class 38 clean/36 ambiguous of 75 → 0 clean/51 ambiguous) — n=1 anchor, suggestive not yet a general claim, but the opposite of the intended effect, so left off pending a broader check. |

## Why `closure_check` is back on

Turned off in the 14/22 baseline as part of a bundled "Variant 1: no fusion at all" simplification (`investigations/2026-07-13-icp-bearing-error-cross-batch-deep-dive/FUSION_MECHANISM_ANALYSIS.md`), alongside `--sequential_pair_disable_temporal_smoothing`. **Important distinction, re-confirmed 2026-07-19**: that investigation's decisive evidence (93.5% of measured fusion-corruption, 7.13% of readings corrupted vs. only 0.48% fixed) was attributed almost entirely to `_temporally_smooth_relocalization` — the across-*time* EMA blend of current's own successive readings, which has no match_class/near_tie trust check at all. `_sequential_pair_closure_belief_fusion` (what `closure_check` actually gates, an across-*role* current-vs-next cross-check) accounted for only the remaining ~6.5% of that corrupted pool — a real but much smaller, and never independently isolated, contribution. Turning it off was a bundled simplification decision, not an individually-proven indictment; disabling temporal smoothing (which stays off in this config) is what the strong evidence actually supports.

## Why `closure_reconciliation_signal` is now `bearing`, and the deferred-reject code fix

**Live mid-batch analysis of `canonical_report_next_50ep_20260719_accumulated` (23/50 episodes in) found `closure_check`, as configured until this edit, was starving `sequential_pair`'s own promotion mechanism on several stuck-anchor episodes** — confirmed by directly importing `route_memory_agent.py` and replaying `_sequential_pair_closure_precheck` against real per-attempt `covisibility_records` data (not inferred from logs):

- `ep5`'s next-candidate pair (anchor 13/12) never promoted across the *entire* 1001-attempt return phase. Replay showed **998/1001 attempts (99.7%) rejected** with `sequential_pair_closure_mismatch`. Root cause: `dtheta` disagreement between the two sides was a stable ~124-136° the whole episode (not random noise) while **position disagreement was consistently small (0.16-0.24m, well under the 0.75m threshold)** — ground-truth reconstruction (via commanded-arclength-to-outbound-step matching, 0.000m verified match error) found anchor 12/13 are only **~0.1m apart in true world position**, roughly 10x closer than the intended ~1.0m anchor spacing, which plausibly makes ICP's independent rotation estimates for the two near-identical local point clouds easy to alias into different solutions even though translation stays accurate.
- `ep678`'s anchor (17,16) pair showed the same pattern: **412/439 (93.8%) rejected**, anchors also reconstructed at ~0.1m true separation.
- Switching `reconciliation_signal` from `dtheta` to `bearing` and replaying the *same* recorded attempts dropped the reject rate to **30.5% (ep5)** and **30.3% (ep678)** — bearing is derived from the same (dx,dy) translation data that was already agreeing, so it doesn't inherit dtheta's noise.
- **`ep187`'s anchor (11,12) pair showed a genuinely different failure**: 74/120 (61.7%) rejected regardless of which reconciliation signal was used (identical reject count for both `dtheta` and `bearing`) — confirmed the rejections there are driven by real **position** disagreement (116/120 exceed the 0.75m threshold), not a dtheta artifact. Switching the signal does not help this case; it is a separate, still-open question (why two normally-spaced, adjacent anchors' independent ICP fits genuinely disagree on position) that this edit does not claim to fix.

**A second, independent bug was found and fixed in the same investigation, in `route_memory_agent.py::_select_sequential_pair_relocalization`**: previously, whenever `_sequential_pair_closure_precheck` returned a reject reason (`sequential_pair_closure_mismatch`), the whole method returned immediately, before the promotion-vote code (`_record_promotion_vote`, `bounded_evidence`'s window/min_votes) or `promotion_alias_stall_attempts`'s own counter ever ran — meaning a persistently-mismatching pair left **zero record** of the attempt ever happening, not even a failed vote. For `ep187`'s 74 silently-dropped attempts, this meant `bounded_evidence`'s 5-window could never accumulate votes from them, and the 200-attempt stall-relief valve (meant to fall back to a more lenient threshold on a persistently-stuck candidate) never advanced its counter on any of those 74 attempts either, delaying it well past when it should have fired. **Fixed to mirror `sequential_pair_short_baseline_require_resolution`'s already-established pattern** (run promotion bookkeeping normally, override only the final decision) instead of dropping the attempt from history: a closure mismatch now forces that attempt's vote to an explicit `False`, so `bounded_evidence`'s window and the stall counter both see it. Verified against the existing test suite: 280/280 tests still pass, zero regressions. This fix does not guarantee a mismatching pair ever promotes — it only ensures the vote bookkeeping and the 200-attempt relief valve behave as originally designed instead of being silently starved; `ep187`-style genuine position disagreement may still take up to 200 attempts to get relief, or may still never cleanly resolve.

**Neither of these fixes has been live-batch-validated yet** — they're applied here based on direct replay against real recorded data from `canonical_report_next_50ep_20260719_accumulated`, not a fresh live run with the fixes active. The next canonical batch launched after this edit is the first real test.

## Why `disable_temporal_smoothing` stays on (i.e. smoothing stays off)

This is the mechanism with the strong, direct evidence (93.5% of measured corruption, ~15x more harmful than helpful) and is not being reconsidered here.

## Why `report_next_anchor` is on

Off in the 14/22 baseline simply because the flag didn't exist yet (created 2026-07-18). Confirmed via real data that the hint had always reported "current" (backward-looking, last-confirmed) despite its own text label claiming "next-anchor vector" — bearing frequently swung to ±150-179° mid-dwell (target behind the robot). Reporting next instead is the architecturally-correct fix; see `--sequential_pair_report_next_anchor`'s own docstring in `round_trip_eval.py` for the full history.

## Why `suppress_if_stale` is on

Enabling `report_next_anchor` alone exposed a real, previously-invisible freezing bug: next's cached estimate (`_latest_next_candidate_relocalization`) only updates when a fresh estimate is accepted, and has **no time/attempt-based staleness handling at all** — confirmed by code inspection that `_propagate_latest_relocalization` (would dead-reckon a stale cached pose forward using real per-step odometry between corrections, wired in since 2026-06-28 per commit `697dc6a`) has **zero live call sites** in the current, uncommitted workstation checkout — the call was silently dropped, most likely an unintentional side effect of the 2026-07-16 `return_frame_buffer_enabled` rewrite of the same function. Quantified on real data: a 22-episode restart batch combining `report_next_anchor` with the (now-excluded, see above) multiframe mechanism showed up to 19 consecutive byte-identical hints (~1075 steps, ~215 underlying ICP attempts, none of which refreshed the value) in a failed episode, vs. a max of 3 anywhere across 34 checked episodes of the 14/22 baseline (33/34 never repeat a hint at all). **The user explicitly rejected reviving the odometry-propagation approach** (odometry drifts too easily to trust for this) — `suppress_if_stale` instead suppresses the hint entirely (falls back to the plain instruction) on any VLM turn where next hasn't been refreshed since the previous turn, rather than either a stale number or an interpolated guess. Implemented and unit-tested 2026-07-19 (6 new tests, 280 total, zero regressions) but **not yet live-batch-validated** — that's what the 2026-07-19 re-launch above is for.

## Separate infra fix landed alongside this (2026-07-19): `main()` now always closes `simulation_app`

Unrelated to the hint logic itself, but fixed in the same session and shipped in the same relaunch: `round_trip_eval.py`'s `if __name__ == "__main__":` block previously called `main()` with zero exception handling, so any uncaught exception (confirmed live: a transient numpy-internals `TypeError` inside `_nearest_neighbor_2d`, unrelated to any of the logic above) skipped `simulation_app.close()` entirely, leaving Omniverse Kit's ~200+ native worker threads running indefinitely — confirmed via `/proc` that a crashed process sat at 106% CPU with 244 threads and 3.5GB GPU memory held for 100+ minutes, until the outer bash 7200s timeout eventually force-killed it (and per the earlier zombie-process investigation, that force-kill doesn't always cleanly reach every one of Kit's own threads either). Now wrapped in `try: main() finally: simulation_app.close()`, so cleanup always runs regardless of how `main()` exits. This plausibly explains a large share of this project's long history of "timeout eats 2 hours" and "GPU memory not released after a crash" symptoms, not just the specific freezing bug this file is otherwise about.
