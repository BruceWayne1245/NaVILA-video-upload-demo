# 2026-07-28 — How the promotion/quarantine/wait model should plug into `route_memory_agent.py` / `round_trip_eval.py`

## Recommendation up front

**Not a plain on/off flag.** Reuse the `reliability_v11_decision_shadow` / `V11ShadowJsonlSession` / `PortableV11Bundle` machinery that already exists in this codebase (`round_trip_eval.py` ~line 2949–2986) almost verbatim, applied to a new bundle type. That existing pattern already solves the three things a bare boolean flag would get wrong for a learned component: model **versioning** (a hash-verified artifact, not a code-level on/off), a **separately-tunable decision-policy layer** on top of the raw model (exactly what §4.1 of `FINDINGS.md` needs — the quarantine threshold), and a **pure-logging shadow mode with zero behavioral effect**, which every prior heuristic change in this project (Injection A/B/C, `quarantine_next_quality`) had to earn through live validation the hard way, one variable at a time, because there was no shadow-first infrastructure for those simpler changes. A model swap is a bigger behavior change than any single heuristic flag flip has been — it deserves the heavier-weight rollout tool this project has already built and validated for exactly this class of risk, not the lighter one built for single-constant threshold tweaks.

## 1. Why not a bare flag

A CLI boolean like `--sequential_pair_promotion_use_model` is how every other mechanism in this codebase is gated, and that convention should stay for the final "is the model authoritative or not" switch — but a boolean alone is missing three things a heuristic flag never needed:

- **Which model.** A heuristic is fully specified by the code plus a handful of numeric constants already echoed into the measurement JSON's config block. A learned model is a serialized artifact that will be retrained as more data/mechanism-A-G fixes land — "the model" is not a fixed thing the way `reliability_quarantine_threshold=2.5` is. Reproducing a run six weeks from now requires knowing *which* model file produced its decisions, not just that "a model" was on. `PortableV11Bundle` already solves this: it's loaded by path, its SHA256 is computed and written into the shadow log and (when the mechanism is `--reliability_v11_decision_shadow`) the measurement JSON. Do the same here.
- **Which decision policy.** §4.1 found the right quarantine operating point is threshold ≈0.6–0.7 on `proba_quarantine`, not the raw argmax the model naturally produces. This threshold should be retunable (e.g., after more mechanism-A–G fixes change what the training distribution looks like) *without* retraining or touching the model artifact. `V11DecisionShadowPolicy` is already a separate, independently-loaded object from `PortableV11Bundle` in the existing pattern for exactly this reason — mirror that split: `PromotionModelBundle` (the GBDT + feature schema) and `PromotionDecisionPolicy` (thresholds: `promote_threshold`, `quarantine_threshold`, `wait` as the residual).
- **Zero-risk observation before any enforcement.** Every heuristic change in this project's history (`2026-07-15`'s `quarantine_next_quality`, in particular) was validated with an *offline* replay before any live run, and even offline replay under-predicted the live regression that run actually showed (single-run A/B is "suggestive, not conclusive" per that document's own words). A model trained on 288 episodes' worth of historical heuristic-driven trajectories has a training/deployment distribution-shift risk a pure heuristic constant does not: once it's live, its own decisions change what anchors get visited and what the VLM sees next, which is exactly the kind of feedback loop offline replay cannot fully capture. The existing shadow session already exists to bridge this gap safely — it runs the candidate policy on *real* live episodes and logs what it *would* have decided, with the banner `enforcement=False controller_effect=False`, before any live behavior change is permitted.

## 2. Concrete plan, phased

### Phase 0 — package the model as a bundle, not a pickle

The prototype `.pkl` from `FINDINGS.md` is not a deployable artifact. Build a `PromotionModelBundle` (new, mirrors `PortableV11Bundle`'s interface) that carries: the fitted `HistGradientBoostingClassifier`, `feature_names` in a fixed order (self-describing — avoids silent feature-order mismatches between offline training and the live agent), the z-score constants used for `U` (currently hardcoded in both `route_memory_agent.py`'s `_reading_unreliability` and the offline extraction script — should be a single source of truth the bundle carries, not duplicated), and a `save`/`load(path, mode)` pair matching `PortableV11Bundle.load(artifact, mode="shadow")`'s signature. Verify the actual eval-loop process (not just the `navila-vlm` conda env used for offline training) has `sklearn==1.2.2` importable at runtime, or export to a dependency-light format (e.g. re-implement the fitted tree ensemble's `predict_proba` from the sklearn model's internal tree structure, or `skops`) if it doesn't — this needs checking before Phase 1, not assumed.

### Phase 1 — port the online feature computation

The offline extraction script's rolling features (`next_dist_rollmean/std`, `cur_bad_fraction_hist`, `attempt_in_dwell`) need a live equivalent inside `RouteMemoryAgent`. Partial infrastructure already exists and should be extended, not rebuilt: `_promotion_distance_history`/`_promotion_score_history` (already tracks a rolling window per candidate index) and `_current_reliability_history` (already tracks `current`'s own `U` history for Injection B's `_current_persistently_unreliable`). Add `attempt_in_dwell` as a simple counter reset on promotion, and rolling std alongside the existing rolling mean bookkeeping.

### Phase 2 — shadow mode (log-only, mirrors `--reliability_v11_decision_shadow`)

New flag `--sequential_pair_promotion_model_shadow` (path to a `PromotionModelBundle`, off/`None` by default). When set: at every relocalization attempt, compute the model's `promote`/`quarantine`/`wait` decision using the live features from Phase 1, log it (episode key, attempt, model decision + probabilities, and what the heuristic actually decided) to a JSONL file the same way `reliability_v11_shadow.jsonl` works today — **but do not act on it.** The heuristic (post-mechanism-A–G-fixes, from the sibling `MODIFICATION_PLAN.md`) keeps making every real decision. Run this at batch scale (the existing ~50–100 ep batches this project already runs routinely) purely to collect agreement/disagreement statistics between model and (fixed) heuristic on live rollouts, and to check the offline-trained model's calibration holds up on genuinely new episodes/scenes it never saw in the 288-episode training set.

### Phase 3 — opt-in live enforcement (matches every other mechanism's convention)

Only after Phase 2 shadow data looks good: `--sequential_pair_promotion_model_active` (off by default). When on, the model's decision (via the tunable `PromotionDecisionPolicy`, not raw argmax) **replaces** the entire current chain in one call — `quality_ok`/`close_enough`/`trend_ok`/`_record_promotion_vote`'s bounded-evidence voting, and `_record_next_anchor_trend`'s quarantine check — for a single, unified per-attempt decision. It does **not** replace the surrounding safety architecture: `reliability_quarantine_max_chain`'s cascade cap still bounds how many consecutive quarantine calls (model-issued or not) can happen between two promotions, and `stop_gate`/`hint_action_arbiter`'s own independent confidence gates (mechanisms D/E/G territory, per the sibling `MODIFICATION_PLAN.md`) stay untouched — this model only owns the promotion/quarantine/wait decision, nothing downstream of it. If the bundle fails to load or errors at inference time, fall back to the heuristic path rather than crashing the episode (defensive default, matching this project's general convention of graceful degradation over hard failure).

Validate exactly like every prior mechanism here: single-variable live A/B against the current canonical config, not combined with the line-2 heuristic fixes in the same launch, so a regression can be attributed to one change or the other.

## 3. What this buys over "line 2" alone

Not a replacement for `2026-07-28-downgrade-batch-mechanism-failure-classification/MODIFICATION_PLAN.md` — mechanisms D (stop_gate corroboration), E (hint_action_arbiter's split confidence bars), F (VLM decision layer), and G (Injection C's threshold) live entirely outside the promotion/quarantine decision this model owns, and still need the line-2 fixes regardless of whether this model ships. What this model targets is specifically A, B, and C — and per §3 of `FINDINGS.md`, it already resolves both fully-frozen mechanism-C episodes (ep276, ep646) at the per-attempt level in a way no threshold-based heuristic (including a hypothetical better-tuned one) can, since it has access to information (dwell position, rolling volatility, current's own reliability trend) those heuristics structurally don't use.
