## 4. Root cause of the 7 physical-wedge (`stuck_recovery`) episodes — they are downstream symptoms, not the primary problem

User's hypothesis going in: the wedges are likely *caused* by upstream anchor-tracking bugs (frozen/stale readings, erratic hint direction), not an independent locomotion failure — so fixing `stuck_recovery` itself would be low-leverage. **Confirmed for all 7/7.** Traced the exact `[stop_gate]`/`[hint_arbiter]` state in the 300–400 steps immediately before each episode's *first* `wedge_detected` trigger:

- **5/7 (ep205/367/368/671/688)** — the next-anchor candidate was already frozen/pinned (same static `anchor_remaining` for hundreds of steps) *before* the first wedge, producing an unstable or bearing-locked hint that walked the robot into an obstacle. ep367's case is the cleanest: hint bearing pinned at exactly `172.87269734511597°` for 150+ steps while `local_map` twice reported that exact direction as occupied — the hint never adapted, so the robot kept trying the same blocked heading until it wedged.
- **1/7 (ep678)** — the wedge came right after a rapid, unhealthy anchor jump (`current_idx` 12→7→6 within ~150 steps, immediately following the `evict_streak=19` near-miss above), with hint bearing swinging >100° between consecutive VLM queries in that same window.
- **1/7 (ep1040)** — hint repeatedly re-proposed a direction `local_map` had *already* reported occupied 3 times in a row, walking straight into it.

**Implication: fixing #2 (eviction) and #4 (frozen-reading distrust) below is expected to reduce wedge frequency as a side effect, without needing any change to `stuck_recovery.py` itself.**

## 5. Stop_gate historical archaeology (2026-07-22 → 2026-08-03) — what's actually been tried, and what's still open

Pulled every `investigations/` folder in that date range mentioning stop_gate/stop-decision behavior (full folder-by-folder catalog available on request; summarized here).

**A "confidently wrong" false-FORCE class recurs independently at least 5 times across 3 weeks, never fully closed**: ep669 (07-22, believed 1.42m vs true 4.60m, rotational error, scalars looked clean), ep93/ep581/ep427 (07-23, "骗停" — an entire downstream anchor chain gets confidently-wrong-matched at once, so BOTH `bounded_evidence`'s gates AND anchor-corroboration's "two independent signals" get fooled simultaneously because they end up being the *same* poisoned identity agreeing with itself), an unnamed short-biased case (08-01), and this session's own ep994. **07-23's own diagnosis: "the root cause is in the promote layer, not stop_gate — stop_gate is a faithful executor of a poisoned upstream signal."**

**Mechanism D (2026-07-28, never previously explained): anchor-corroboration's veto looked like it should have fired on ep205 (d=10.76m≫r_out, anchor remaining=7.05m≫r_in) but the logged decision was `deferred`.** Root-caused this session (fix #1 below): Injection C's `distance_authority_low_reliability` early-return sits *before* the anchor-corroboration veto check in the code and returns unconditionally — so whenever the same reading is *also* flagged low-reliability, corroboration's veto (explicitly designed to not depend on this reading's own quality — the FORCE path already ignores this flag entirely) never even gets evaluated. A genuine ordering bug between two mechanisms shipped 2 days apart that had never been tested together for this interaction.

**Mechanism E (07-28) — already fixed by 08-03's `hint_action_arbiter_stop_veto`.** No new work needed.

**`estimate-freeze` bug (07-23, ep1062: believed distance pinned at 4.0m, hint bearing pinned at 11°, entirely unchanging — explicitly flagged as "low-hanging fruit" and NOT the same thing as confidently-wrong) — still unfixed as of the 08-03 batch (this session's ep368, 12+ days later).** Directly closed by fix #4 below.

**An isolated Route2 branch (`investigations/2026-07-28-anchor-support-recovery` / `terminal-stop-evidence-state-machine` / `anchor-stop-active50-readiness`) independently built and validated a full 5-state alternative stop-decision architecture** (`navigating → terminal_verify → terminal_blind → arrived/safe_fail`), central principle: **"a VLM STOP is a proposal; only positive terminal evidence may turn it into success" — `deferred` is eliminated entirely.** Named the same root causes this session independently re-found: low-confidence `deferred` is, in effect, an unconditional accept (08-01's own data confirms this actually happened: the same false "I'm home" VLM claim was correctly vetoed once at high confidence, then let through later purely because confidence happened to read low that attempt); no distinction between current's (structurally-late) and next's (structurally-early) authority to end an episode. Live counterfactual replay against 9 known failure episodes: 0 unsafe outside-radius accepts, ep89/ep490's historically-infinite veto loops (60/148 vetoes) bounded into `safe_fail`. This is a different codebase (not `NaVILA-Bench/scripts/stop_gate.py`), not directly mergeable, but its *design principles* are exactly what fixes #2 and #5 below port into Route1's own file.

## 6. What was implemented today — 5 opt-in fixes, plus this session's explicit enable/don't-enable recommendation

**Convention followed throughout, matching this project's own established practice:** every new flag defaults OFF (byte-identical behavior unless explicitly passed) — this is a code-safety property, not a recommendation about what to actually run. **Section 6.1 states plainly which ones this session recommends turning ON for the next validation batch, since defaulting-off and then never actually enabling a fix in any launch script is its own failure mode this project has hit before** (yesterday's ambiguity_gate had zero live confirmation for exactly this reason — nobody had a way to check whether it fired at all).

| # | Flag(s) | File | What it does | Recommend enabling? |
|---|---|---|---|---|
| 1 | `--stop_gate_corroboration_overrides_low_reliability` | `stop_gate.py` | Mechanism D fix: lets anchor-corroboration's veto fire even when Injection C also flags the reading low-reliability, instead of being silently skipped. | **YES.** Narrow, well-justified, directly closes a 12-day-old unexplained discrepancy. Low risk — only changes behavior when corroboration's own two conditions are independently satisfied. |
| 2 | `--current_evict_mode=window --current_evict_window=40 --current_evict_min_votes=30` | `route_memory_agent.py` | Redesigns eviction from a hard consecutive-streak (resets to 0 on one good-looking reading) to a bounded sliding-window vote (tolerant of an occasional blip) — motivated directly by ep678's evict_streak=19/30 near-miss. Requires `--sequential_pair_evict_unreliable_current` to already be on (it is, in every recent batch). | **YES.** This is the single most directly-motivated fix from real batch data this session found. |
| 3 | `--sequential_pair_promotion_anomaly_gate --sequential_pair_promotion_anomaly_max_bearing_jump_deg=90 --sequential_pair_promotion_anomaly_max_collapse_m=1.5` | `route_memory_agent.py` | The 07-23-proposed-but-never-built cheap vision-free anomaly check: blocks promotion when a candidate's bearing jumps >90° or its distance collapses >1.5m versus its own previous attempt (ep93's real signature: collapsed >2x the true rate). | **YES.** Directly targets the "confidently wrong" false-FORCE class's root mechanism (07-23's own diagnosis: root cause is in the promote layer). Zero live data yet — this batch is its first real test. |
| 4 | `--sequential_pair_stale_relocalization_distrust --stale_relocalization_max_attempts=30` AND `--sequential_pair_relocalization_uncertainty_mode=growing --stale_uncertainty_base_floor_m=0.35 --stop_gate_use_uncertainty_interval` | `route_memory_agent.py` + `stop_gate.py` | Two combinable variants of the same fix: a role's cached estimate silently stops refreshing (ep368, ep1062) with nothing downstream able to tell. "Fixed" mode: hard threshold, cap confidence + defer once 30 attempts stale. "Growing" mode: continuously-widening uncertainty radius from the *first* stale attempt (mirrors the Route2 branch's own `[d-0.35, d+0.35]`-style interval), consumed by stop_gate to require the worst/best case (not just the point distance) to clear r_in/r_out. | **YES, both together.** This is ep368's exact fix, and the two modes are complementary (fixed = hard backstop, growing = earlier, gentler response) — this session's design explicitly allows combining them. |
| 5 | `--stop_gate_blind_budget --stop_gate_blind_budget_max_attempts=8` | `stop_gate.py` | A `distance_authority_low_reliability`-driven `deferred` is, in effect, an unconditional accept with no limit on repetition (08-01's own documented failure case). Once 8 consecutive attempts have had zero trustworthy distance authority (tracked regardless of whether the VLM has proposed a stop, closing ep89's "reached home, never proposed stop" blind spot too), treat a would-be `deferred` VLM-stop like a veto instead. Does **not** end the episode outright — that needs a separate, explicitly-reviewed change to the main step loop, deliberately not bundled here. | **YES.** Directly ports the Route2 branch's most load-bearing design principle, using only existing decision-consumption plumbing (no new round_trip_eval.py dispatch logic). |
| 6 | `--stop_gate_require_cross_role_agreement --stop_gate_cross_role_max_disagreement_m=1.5` | `route_memory_agent.py` + `stop_gate.py` | current and next roles' ICP matches come from *different* anchors' point clouds — a genuine independent cross-check, unlike anchor-corroboration's reuse of the same reading. FORCE and ACCEPTED both now additionally require the other role's own independent distance to agree within 1.5m; missing data (other role has no live estimate) is treated as "cannot verify," not "disagrees," and never blocks. | **YES.** Most direct available mitigation for the still-unsolved "confidently wrong, same identity agreeing with itself" root cause (§5) — a genuinely different signal from everything else on this list. |

**All 6 recommended for the next batch.** This is a deliberate departure from the "one flag at a time" single-variable-A/B principle this project's own FINDINGS.md has repeatedly (and correctly) argued for — flagged explicitly here, not silently: bundling all 6 makes individual attribution impossible if the batch's aggregate number moves. This session's judgment is that a first comprehensive pass is more valuable right now than 6 separate 30ep batches given current batch-noise levels (§1's 4:1 flip ratio on a *config-identical* rerun shows individual-episode attribution needs a much larger n than 30 anyway) — but if this batch's result is surprising in either direction, the natural next step is exactly the single-variable-A/B sequence this project's convention calls for, now that all 6 flags exist independently and can be toggled one at a time.

**Not touched: Mechanism G (Injection C's `reliability_quarantine_threshold=2.5` sitting just above real near-misses, e.g. ep366's U=1.85–2.14).** Lowest priority per explicit user instruction — hard-threshold softening has a bad precedent in this project (the 07-05/07-07 fusion-corruption saga was caused by exactly this kind of blending).

**Testing**: 419 total tests (up from 362 at the start of today), same 1 pre-existing unrelated `cv2`-import failure, 14 pre-existing skips, **zero new regressions** across every incremental change. All 6 flags confirmed to combine without crashing (constructed together in one smoke script). `code/stop_gate.py` and `code/test_reliability_gating.py` in this folder carry today's changes in full. `route_memory_agent.py`/`round_trip_eval.py` are not included in full (too large, both already carry a large unrelated pre-existing uncommitted diff — same exclusion `investigations/2026-08-03-model-rollback-and-line2-phase0-1-resume` made) — every new block in those two files is described above with exact flag/function names to relocate and reapply directly.
